# orchlog analysis — baseline at workflow 1.9.0

- **Date:** 2026-08-06
- **Log:** `~/.claude/orchestrate/runs.jsonl` (583 lines)
- **Window:** 76 runs, 382 agent records, 2026-06-30 → 2026-08-04, schema 1.7.0–1.9.0
  (token attribution trustworthy from 1.7; wave shapes and derived counters from 1.9)
- **Purpose:** the *before* snapshot for the 2.0.0 changes (two-dimension gate + linear-chain
  collapse). Re-run this analysis after ~30 logged 2.0.0 runs and compare section by section.

## Headline

| Signal | Value |

| Runs logged | 76 (36 at schema 1.9.0) |
| Run outcome | success 76/76; final build green 100%; final tests green 98% |

## Finding 1 — small runs pay a ~4.5× orchestration tax (HIGH; addressed in 2.0.0)

Orchestration overhead (planning, briefs, integration, reviews, logging) is roughly fixed per
run, so its relative cost explodes as runs shrink. Per-run orchestrator/implementer output-token
ratio, over the 28 schema-1.9 runs with clean attribution:

| Run size | n | Median orch/impl ratio |
|---|---|---|
| ≤5 agents | 13 | **4.46×** (worst: 20.1× on a 2-agent run, 12.7× on 3, 10.2× on 4) |
| 6–9 agents | 8 | ~1.0× |
| 10–16 agents | 5 | ~1.38× |
| 17–22 agents | 2 | 0.63–0.72× |

Break-even (~1×) sits around **6–7 agents**. The `W ≥ 2` width gate (hardened in 1.9) eliminated
fully-serial runs — every 1.9 run has real parallelism, versus a 25% `peak_width == 1` leak
before — but small-parallel runs (2×2 shapes) passed it at full cost.

**2.0.0 change:** gate is now width `W` AND volume `V` (tasks after chain collapse). `W ≥ 2` but
`V ≤ 4` → direct dispatch (parallel implementers, full briefs, no run record / wave machinery /
standing review loop). `V ≥ 5` → orchestrate.

**After-metric to watch:** direct-dispatch runs are *unlogged*, so expect fewer, larger logged
runs. Compare: share of logged runs with `agents_total ≤ 5` (baseline: 13/28 ≈ 46%), and median
orch/impl ratio (baseline: 1.46×, should fall toward ~1.2× as the small tail disappears).

## Finding 2 — serial chains hide inside parallel runs (HIGH; addressed in 2.0.0)

14 of 36 schema-1.9 runs (~40%) contain **2+ single-agent waves**, mostly dependent chains
(shapes like `[3,1,1,1]`, `[2,1,1,1]`, `[3,1,1,1,3,1]`). Each width-1 wave is a full
dispatch → report → integrate round trip banking zero parallelism.

**2.0.0 change:** partition rule — consecutive width-1 tasks merge into one implementer with a
multi-step brief; split only when something runs beside the task or the chain exceeds one agent's
context. `/taskplan` collapses chains before deriving waves.

**After-metric:** avg waves/run (baseline 3.2) and share of runs with 2+ width-1 waves
(baseline ~40%) should both fall; avg agents/wave should rise.

## Finding 3 — Haiku routed too aggressively (MEDIUM; guidance only, not yet changed)

Rework by tier: **haiku 3/21 (14.3%)** vs sonnet 7/200 (3.5%) and opus 4/90 (4.4%). Haiku is 5%
of dispatches, so savings are negligible while each miss costs a re-dispatch a tier up. Its failed
tasks ("PRStatusCacheTests TTL boundary 300s", "tilde markdown strikethrough") involved real
correctness judgment, not mechanical edits.

**After-metric:** haiku rework rate; if it stays ≥10%, narrow the routing table in step 3 of
`/implement` or drop the tier.

## Finding 4 — output tokens concentrate in the orchestrator

Across all token-attributed runs (schema ≥1.7): orchestrator 27.86M output (69%),
code-implementer 8.46M (21%), review 2.49M (6%), Explore 0.82M (2%), other agent types 0.42M
(1%). This is the structural cost Finding 1's gate attacks; the fix is orchestrating less often,
never planning less.

## Finding 5 — boundary stops cluster in wiring/e2e tasks (MEDIUM; open)

All 16 boundary stops are cross-cutting task types: app/controller/overview wiring, MCP tool
registration, e2e suites. Partitioning should give these deliberately wide boundaries (enumerate
registry/DI/route files) at plan time.

## Finding 6 — token-capture blind spots (MEDIUM; open)

- All 4 `/implement-orca` runs logged **zero token data** — workers are external `claude` CLI
  sessions invisible to the transcript scan. Consider a `--mode orca` tag on run records, or
  scanning the workers' own project transcript dirs (cwd → sanitized path is derivable).
- 4 further runs captured `Explore`/`orchestrator` buckets but `code-implementer == 0` despite
  having implementers (missing `.meta.json` `customAgentType`?). `record --type run` should warn
  when `agents_total > 0` but the implementer bucket is empty.

## Finding 7 — minor signal inconsistencies (LOW; open)

- One run has `outcome: success` with `tests_final != pass`; `report` shows 100%/98% side by side
  without flagging it. Define or flag.
- `deviated` is a boolean (26% overall; opus 34%) and can't distinguish "improved on the brief"
  from "missed criteria". Consider `--deviation-kind criteria-gap | scope-add | better-approach`.

## Working well (keep)

- Hardened `W ≥ 2` gate: zero serial runs at schema 1.9 (was 25% before).
- Review loop: ~5.7 findings/run consolidated into ~2.4 fix agents.
- Rework at 4.2% with escalate-on-rework holding; builds green on every run.
- Version-stamped records — this comparison is only possible because of them.
