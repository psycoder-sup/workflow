# Ticket brief template

The brief handed to each ticket's `code-implementer` subagent. One brief = one ticket = one fresh
context window; the implementer shares no memory with this session or with any other ticket's
implementer. Front-load everything. Interpolate the ticket's real values; don't send placeholders.

## Which text is the contract

Fetch the issue **with comments** (`gh issue view <n> --comments`) and pick by origin:

| Ticket origin | The contract | Send |
|---|---|---|
| `/to-tickets` — you authored it | the **issue body** (What to build / Acceptance criteria / Blocked by) | the body verbatim |
| `/triage` — it arrived from someone else | the **agent brief comment** posted when it moved to agent-ready | the agent brief verbatim, **plus** the body under "Original report" |

This distinction is load-bearing. `AGENT-BRIEF.md` states it directly: *"The original body and
discussion are context — the agent brief is the contract."* On a triaged issue the body is a user's
raw bug report; sending it as the spec hands the worker the symptom instead of the work.

Recognise an agent brief by its structure (a `## What to do` / acceptance-criteria comment from the
maintainer) and by the AI-triage disclaimer `> *This was generated by AI during triage.*` If an
issue is labelled agent-ready but carries **no** brief and **no** acceptance criteria in its body,
don't dispatch it — refuse it as under-specified (Step 0's guard should have caught it).

**Paste verbatim either way.** A paraphrase silently drops acceptance criteria.

---

```text
## Task

Implement GitHub issue #<n> — <title> — as one vertical slice on the current branch.

<the contract verbatim — see "Which text is the contract" above: the issue body for a
/to-tickets ticket, or the agent brief comment (plus the original report as context) for a
triaged one>

The acceptance criteria above are the contract — verify against them, not against vibes.

## Before you write anything

Read `docs/agents/domain.md` and follow it. In short: read `CONTEXT.md` (or `CONTEXT-MAP.md` and
the contexts it points at) and any ADRs under `docs/adr/` that touch this area. Name things using
the glossary's vocabulary — if a concept you need isn't in it, that's a signal: either you're
inventing language the project doesn't use, or there's a real gap worth noting. If your approach
contradicts an ADR, STOP and report rather than quietly overriding it.

If those files don't exist, proceed silently — they're created lazily, and their absence is normal.

## How to build it

This ticket is ONE vertical slice — a narrow but complete path through every layer it touches.
Build it serially, yourself. Earlier tickets in this feature have already landed on this branch;
build on what's here.

Work test-first at the seams the spec named: write the failing test (red), then the minimal code to
pass it (green), then refactor. Test the seam's external behaviour, not its internals. Run
typechecking and the relevant test files as you go, and the full suite once at the end.

## Verification

<the exact build / test / lint commands for this repo>

## Rules

- Read before you write; follow surrounding conventions; reuse existing utilities.
- Stay inside this ticket. Work that belongs to another ticket goes under follow_ups in your
  report — don't fix it here, even if it's one line.
- **Do not commit, push, branch, or open PRs — you only change the working tree.** The
  orchestrator verifies and lands your work as a commit.
- If the acceptance criteria leave a real design fork open, STOP and report it as a blocker rather
  than guessing — a re-dispatch with a ruling beats a reworked wrong guess. Note trivial departures
  under deviations.
- Self-verify before reporting; never claim done on a red build.

## Output

Return the IMPLEMENTER REPORT block exactly as your agent definition specifies.
```

---

## Notes for the dispatcher

- **Paste the contract verbatim.** Every summarisation drops an acceptance criterion.
- **No file-ownership section.** That's the wave path's safety boundary. A ticket legitimately
  touches every layer, and in the serial walk nothing runs beside it — the branch is the boundary.
  The one exception: tickets dispatched as a **fan-out wave** (SKILL.md Step 2) were judged
  file-disjoint first; add a one-line ownership note to each brief in that wave naming the areas it
  must stay inside, so the disjointness you judged is the disjointness they keep.
- **"Earlier tickets have landed on this branch" is true by construction** — the walk order
  guarantees every blocker's slice is already in the tree. Don't list the landed tickets in the
  brief; the code is the context, and the implementer reads the tree, not the history.
- If the repo has no `docs/agents/domain.md` (`/setup-matt-pocock-skills` never ran), drop that
  paragraph rather than pointing the worker at a file that isn't there.
- Fill `## Verification` with the repo's real commands (from CI config or package scripts) — an
  implementer that has to guess the test command wastes its context discovering it.
